# Development notes

Technical notes for contributors. For installing and using the client, see the [README](../README.md).

## Building with the shared core

The desktop and Android clients share [AFMDataClientCore](https://github.com/JPCodeCraft/AFMDataClientCore). This repository pins its library at `shared/AFMDataClientCore`; no sibling checkout or NuGet feed is required to build.

```bash
git clone --recurse-submodules https://github.com/JPCodeCraft/AlbionDataAvalonia.git
cd AlbionDataAvalonia
git submodule update --init --recursive
dotnet restore AlbionDataAvalonia.sln
dotnet build -c Debug AlbionDataAvalonia.sln
dotnet test PowBench.Tests
```

After switching branches or pulling a change to the submodule pointer, run `git submodule update --init --recursive` again. Shared changes are committed and pushed in AFMDataClientCore first; each client then updates its pinned commit independently. A standalone development checkout can live beside the clients at `Repos/AFMDataClientCore`, while builds always reference the pinned submodule.

`DesktopClientCore` explicitly enables market orders (including loadouts), market history, specs, EMV, islands, gold, and world events. It adapts desktop settings, account credentials, and upload statistics to the shared runtime. Activity, party, awakened items, market mail, and trade history remain desktop services and subscribe after shared packet processing. Capture drivers, database schemas, installers, and UI stay in the desktop repository.

The app embeds gzipped base copies of its reference data (items, locations, achievements, mobs and awakened-item data) from `AlbionDataAvalonia/ReferenceData`. They are used only when a file cannot be downloaded and has no validated disk cache yet, such as a first start without access to the CDN. Run `AlbionDataAvalonia/ReferenceData/update.sh` before a release to refresh them from the CDN.

Shared-library integration validation includes building the desktop solution and running the PoW correctness tests. Manual checks cover ordinary and loadout market routing, gold and bandit uploads during Private Mode, authenticated specs/EMV/world events, local tracker updates, account/server changes, and island collection, failed actions, offline retry, and restart recovery. Cross-platform capture and UI checks require the corresponding operating systems; builds alone do not validate live game traffic.

## How Activity records

Activity combines **Current**, **History**, **Items**, and **Cleanup**. Sessions contain encounters and activity between fights; session totals include every assigned event directly. Personal and Party filters use membership saved when each event occurred. Party includes your character. Items also supports All observed and source filters for loot, gathering, and fishing. **Total Silver** and **Total Silver / Hour** combine cash pickups with estimated loot, gathering, and fishing value for the selected period and scope; their tooltip explains estimates and missing values. **Loot value** includes loot only; gathered items, their EMV, and Gathering Fame share the gathering panel.

Current includes a rolling **5, 10, or 15 minute** timeline with damage/healing areas, grouped outcome and reward markers, and encounter combat spans. Nearby rewards are grouped more strongly for longer windows. **Dealt / Received** changes the health series. Hover holds the display while recording continues; moving the mouse out resumes it automatically. Markers show compact tooltips. Hovering an encounter span shows its location, combat time and saved totals for the selected scope (damage, healing, fame, silver, loot, kills, deaths), and clicking it opens the encounter in History. History charts use the same display over the whole session or selected encounter, with at most 600 rate bins. The graph includes idle zeros; headline DPS/HPS uses combat time. Capture gaps are shown separately from downtime. **Gathering** chart mode shows harvested and fished items per second on a separate scale. **Show** filters apply to charts and events, leaving whole-period cards unchanged; selected categories match any. History **Contains all** tags match every selected tag. Loot and silver in PvE/PvP views remain earnings observed during matching encounters; fame uses its independently matched source.

Relevant damage or attributable healing opens an encounter and refreshes its seven-second inactivity deadline. Loot, silver, fame and outcome signals never extend combat. Encounter DPS/HPS uses the first-to-last combat span with a one-second minimum. Encounter earnings mean **observed during the encounter**, without claiming the fight produced them.

While a play session runs, entering any map other than a city, island or hideout opens a run at once, so a run with no activity is still saved with its path; in town only relevant activity opens one. Supported dungeon floors can continue one run. Known-instance reentry within two minutes can resume a run when no intervening relevant activity or local lethal death prevents it; an empty run in between doesn't. Roaming survives ordinary zone changes and ends on hub return, instance entry, Finish, character/server change or 30 minutes without relevant activity. Session DPS/HPS uses the combined combat spans of encounters with activity in the selected scope, excluding time between fights and the closing delay. Earnings per hour use observed session time, including travel and downtime but excluding explicit capture gaps and dungeon-exit intervals.

Mob counts require prior personal/party damage in the same lifetime. Explicit zero health confirms terminal evidence; omitted resulting health is labelled inferred. Visibility departure does not imply death. A dead player who acts or is healed again counts as respawned or revived. Cash silver stays separate from estimated loot value. Only canonical silver pickups contribute cash; overlapping broadcasts remain supplemental. Omitted tax fields count as no tax for you and your party members alike. Reported healing is preserved without claiming effective healing.

**Combat Fame** and **Gathering Fame** are separate; Gathering Fame includes fishing, with a fishing breakdown in its tooltip. Fame awards match preceding Destiny Board progression on the same actor and reliable Photon stream, within four messages and 250 ms. The achievement reference's `killmobfame`, `gatherfame`, and `fishingfame` mission types identify the source independently of the active encounter. Missing or conflicting source evidence remains Unknown. Progress updates never create additional awards. The captured positive bonus is applied once to the award; cumulative player fame is retained only as detail. Existing awards with saved, valid components are corrected when their old calculation can be reproduced, but historical source categories are not guessed. PvP fame packet meanings remain unverified; player kills and encounter types cannot supply a fame amount.

Gathering and fishing packets can also report an additional progression component. When components 12/13 are valid, positive, equal, and the source is matched, one component is added to the ordinary award. This component already includes its applicable bonuses; applying premium or the reported bonus to it again would duplicate them. Captures with and without a reported bonus verify the resulting progression increment. Saved rows without these components cannot safely be reconstructed from ordinary fame.

Inventory requests create short-lived candidates. Your pickup is recorded when the server confirms the exact transfer into your inventory, or into a bag or equipment slot named by your own request; when a unique source decrement matches a gain in your inventory; or when the requested item leaves its loot container, which also covers stacks merged into existing inventory stacks. Banks, rearrangements and failed requests do not contribute personal/party earnings. Party chests attribute pickups to the player named by the loot allocation, and type-only removals to the single party member allowed to open that chest, unless your own pending request or an already recorded pickup explains the removal. A removal already explained by a pickup broadcast is not recorded again. Correlations follow capture time, and pickups still inside their correlation window are resolved before a map change, **Finish** or disabling recording. Pickups seen before the character and map are confirmed are kept outside sessions; party members among them are recognised from the party roster, which is kept across the first map join. Removals without a known recipient, and items missing from a public chest when it is reopened or emptied, are kept as inferred pickups by Unknown; they are shown and exported but not included in totals. Item names come from reference data whenever a pickup omits them. Loot is valued with the Black Market estimate when available, then the normal estimate; pickups without quality use the average of qualities 1-4, labelled in their tooltip. Gathering and fishing keep normal-quality estimates. Known estimates are frozen; missing prices may be filled later through the existing authenticated, batched EMV lookup and cache. Opening item history also requests missing estimates. Looter and looted-player guild and alliance come from the player directory, including players seen on earlier maps, and are completed for recent pickups when a player's identity arrives. Loot lists show them as Guild/Alliance (looter) and Source guild/Source alliance (looted player) columns, and loot search matches both. **Export loot…** on Current, a History session or Items exports exactly the loot list shown there, across all pages. History remains until explicitly deleted. Disable **Activity recording** to close current recording while keeping history readable; **Finish** permanently ends that session.

**Cleanup** shows Activity storage, the whole local database size, and session, encounter, event, and pickup counts. Preview removal of old history or loot picked up outside your party, then confirm deletion. Open sessions and original gathering records are kept. Deletion updates surviving totals and prevents pending amendments from restoring removed events. Freed SQLite space is reused; the file need not shrink immediately.

The journal batches writes every second or 250 changes. Database failures retain accepted work and visibly suspend recording if needed; the session records a gap, keeps the current map, character and inventory context, and resumes recording when writes are accepted again. A write the database rejects as invalid is logged and dropped instead of blocking later writes. A capture restart within a minute (adapter change or traffic recovery) records a gap and continues on the same map and character; after a longer stop, recording waits for fresh identity/map confirmation. When the server IP is not recognised (VPN or routing tools), activity is kept under the last known server, or server 0. Traffic silence is not logout. Process restart marks unfinished activity Interrupted. Shutdown drains recording before disposing capture/core services. Existing SQLite backups include Activity tables.

Debug builds log raw Activity packet probes when **Logs → Log verbosity** is **Debug** or **Verbose**. Probes cover every Activity subscription and inventory intent, plus resource identities, harvest/fishing lifecycle, and achievement/journal progression for fame-source investigation. Event, request, and response logs retain all supplied parameters, capture time, and transport identity; responses also include the result code. Information or higher stops packet probes.

The Activity schema is provided by the EF-generated `20261007145317_AddActivityJournal` migration. Existing startup database initialization applies pending migrations when the application is launched. Do not hand-edit migration files; generate future schema changes with EF Core commands.

### Gathering and fishing

Confirmed harvests from your character or party and confirmed local fishing rewards are recorded by Activity. They start or refresh the session inactivity deadline, but never start or prolong an encounter. Sessions receive Gathering, PvE, and PvP tags from the events visible in the selected scope; a session can have several tags. Fishing is part of Gathering and can also be filtered separately. Fame remains a packet award, and cash silver stays separate from all item estimates.

Fishing requires a successful completion response, a server reward, and a unique matching gain in your inventory. A completed catch is kept when you cancel, move items or leave the map right after it, catches that merge into older inventory stacks are recognised, and catches are settled on capture time so delayed processing cannot drop them. Shared inventory claims prevent the same acquisition from counting as both loot and fishing. Requests and ambiguous rewards are not personal earnings.

Existing gathering history is converted automatically at startup into closed Activity sessions with item summary records. The original gathering tables and rows remain untouched. Conversion preserves stored quantities, values, dates, and observed duration; it does not invent individual pickup times, map locations, fame, cash, or combat. Imported runs are labelled as summaries and have no temporal chart or encounters. Valid orphan checkpoints become partial Interrupted sessions; completed records take precedence. Conversion uses deterministic identifiers and durable import markers, so rerunning it does not duplicate runs or restore deleted Activity history. Invalid records and inconsistent totals are reported while the source data remains intact. This conversion uses the existing Activity schema and needs no additional migration.

## Private Mode and sharing

Private Mode saves all captured buy/sell orders, including loadout offers, to your
AFM account for the flipper and website price tools. No market-order categories
are also sent to AODP. Market history, gold prices and bandit events remain public.
Private Mode and both sharing choices default off and are saved in UserSettings.json.
All three survive restarts, sign-out and account changes. Turning Private Mode off
keeps the sharing choices saved for when it is enabled again. Sharing only applies
to private orders while signed in; private order uploads are skipped while signed
out, without a public fallback or an offline queue.

Settings > Sharing accepts a user ID, email or exact AFM website username in one
field. The website username is not an Albion character name. Both users must add
each other; up to five friends are supported. Ambiguous matches are rejected; use
email instead. Existing entries remain tied to the saved account if a username
changes. Private and shared price summaries expire up to 48 hours after their
five-minute observation bin starts. Turning sharing off affects new uploads only.

Release validation: enable Private Mode and both sharing choices, restart, sign
out and sign back in (also with another account); verify all choices stay selected.
Turn Private Mode off and back on, then disable each sharing choice and repeat
restart/sign-out checks to confirm both enabled and disabled values persist. Capture an
ordinary item and each former public exception (runes, souls, relics, alchemy
extracts and fish sauce), including loadout offers, and confirm no market orders
reach AODP. Verify history/gold/bandit uploads remain public. Check tooltips and the
Sharing field on a narrow window, and add/remove friends by all three identifiers.
These UI/capture checks require a signed-in client and live game traffic.

### Resource mobs

The live map's resource mobs are named by `AlbionDataAvalonia/Activity/ActivityResourceMobCatalog.g.cs`, generated from the game's `mobs.json` (the Harvestable loot of each mob). Regenerate it after a patch adds mobs:

```sh
curl -sSLo /tmp/mobs.json https://raw.githubusercontent.com/ao-data/ao-bin-dumps/master/mobs.json
python3 scripts/generate-resource-mobs.py /tmp/mobs.json
```

The first resource mob of each map logs its NewMob parameters at Information level, for checking the packet layout read in `ActivityResourceMobs`.

### Live wisps and event markers

`ActivityWisps` classifies solo/duo portal mobs from the existing mob catalog. Game `mists.xml` difficulty levels 0–4 map to common, uncommon, rare, epic and legendary; their internal suffixes are respectively empty, `_STANDARD`, `_UNCOMMON`, `_RARE` and `_LEGENDARY` (also after `_DUO`). Do not infer displayed rarity from the suffix's English word. The mapping can be checked against [mists.xml](https://github.com/thecatontheflat/ao2d-gamedata/blob/master/mists.xml). Verdant resource wisps and power-crystal mobs are separate game types and aren't classified as solo/duo portals.

The tracker reuses the existing raw NewMob/Move observations; Leave marks sightings out of view and death removes them. Process-local Live memory restores observations on map revisits and has no resource audio side effects. `MapShowWisps`, `MapWispRarities` (five bits) and `MapWispSizes` (solo/duo bits) persist the layer and minimum rarity and independent solo/duo filters. No new packet parser or submodule update is required.

Live Kills, Loot and Gathering markers default off via `MapLiveShowKills`, `MapLiveShowLoot` and `MapLiveShowGathering`; an explicit choice persists. History keeps independent session choices, initially on. These are display preferences and do not disable recording. No database migration is needed.

### Depths map

AlbionWorld has no minimap or map features for the Depths, so `AlbionDataAvalonia/Maps/DepthsMapData.g.cs` brings each floor from the game's hell dungeon files: its rough ground outline, camp slots, exits and chest, coffer, key and shrine spots. Regenerate it after a patch changes the Depths:

```sh
git clone --depth 1 --filter=blob:none --sparse https://github.com/ao-data/ao-bin-dumps.git /tmp/ao-bin-dumps
git -C /tmp/ao-bin-dumps sparse-checkout set --no-cone /helldungeons.xml /helldungeonstemplatemetadata.xml '/templates/DEAD/HELLDNG_*' /cluster/tiles.xml
python3 scripts/generate-depths-map-data.py /tmp/ao-bin-dumps
```

Joining the Depths can name no layout (the map id is only `@HELLDUNGEON@<guid>`). Floor counting remains a fallback label; fixed landmarks determine the actual floor and orientation. `DepthsMapData.Recognize` compares upward, downward and soul exits, resurrection shrines and demon altars against all three masters at all four quarter turns. It requires two distinct matching template points and an unambiguous lead over other placements. Slave-section objects are ignored as outliers. Coordinates remain in the template frame; the old hard-coded half turn has been removed.

`ActivityPacketSubscriptions` reuses the shared world-object envelope decoder (`MistsLandmarkEvent`, key 0 object id and key 1 position) for the five corresponding object-spawn events. This does not change Photon decoding or the pinned shared core. Observations are limited by connection identity, capture time and map binding, including a short pre-Join window on a new connection. Recognized placements are kept per server, character and exact map id until app exit, and re-evaluated when more landmarks arrive. Live and History use the existing `Layout`/`LayoutTurns` metadata; no migration is needed.

A Join request also opens a pending Depths landmark window. Spawn events received before its response are tagged with that attempt, even when it reuses the current socket, and cannot change the map being left. A successful Join binds only matching-connection observations from the last ten seconds to the newly confirmed server/character/map key before recognition runs. Landmarks observed on the old map before the request, failed/superseded attempts, other receiver generations and stale bursts are excluded. This fixes the same-socket pre-Join case where every altar was previously bound to the old map and discarded after entry; walking did not necessarily resend those spawn events.

`DepthsMapData.Analyze` preserves the recognition threshold and exposes distinct observed landmarks, the best matching count and competing matches. Live snapshots carry recognition progress and invalidate the scene when it changes, including before a placement is accepted. The waiting banner distinguishes no received landmarks, partial/ambiguous matches and received coordinates that do not match the bundled templates. Opt-in packet diagnostics include match progress and one malformed-envelope note per landmark kind/map epoch, alongside the existing raw packet dump; no raw packet parameters are added to normal logs. If a live instance still fails, capture diagnostics from before entering through several visible altars/exits and compare the five subscribed event envelopes and coordinates with the templates. The fix is verified with decoded synthetic traffic through the production subscribers, not a captured Windows gameplay session.

Until orientation is confirmed, the UI shows the world-space path and observations on a grid, with a waiting message. Static rooms, outline and possible POIs stay hidden. Once confirmed, rooms, outline and POIs all rotate together; observed player and entity positions never rotate. Old History visits without a confirmed Depths turn remain on the grid rather than assuming 180 degrees. Validate the object envelopes against a live Windows capture after protocol changes; the offline fixture only verifies decoded synthetic packets and template geometry.


## Hostile alert audio

`HostileAlertSoundService` subscribes to confirmed hostile arrivals from `ActivityTrackerService`, independently of the map window. Audio requires the Hostile alert layer and sound toggle to be enabled, active capture/context, a current non-hub/non-blue zone, and an arrival less than three seconds old. Bursts are coalesced for three seconds per map epoch; an active sound is never queued or overlapped. Replays do not emit arrivals. Shutdown, disabling the alert/sound, muting or changing the file cancels playback.

Transient hostile indicators and both sound arrivals start their lifetime at application observation time. Capture-driver timestamps still govern packet ordering, map/connection validation and journal records, but are not compared with playback/UI wall time to expire a newly observed alert. This prevents capture-clock drift from immediately expiring every alert during a long session. A warning records the capture/observation offset once per map epoch when outside the alert window; it may also indicate delayed processing, so it does not by itself prove driver clock drift. Delayed packets accepted in the current map produce an alert when processed; wrong-map and pre-entry packets remain rejected. Sound burst cooldowns use `TimeProvider` monotonic timestamps, so system clock adjustments cannot prolong or bypass them. Playback waits for the track duration plus five seconds (30 seconds when duration is unavailable), then stops and releases the device if its completion callback never arrives. The next arrival can retry rather than leaving that alert service permanently busy. No setting, schema or dependency changes are required.

Playback uses SoundFlow 1.4.1 (MIT) with its packaged MiniAudio runtime on Windows, Linux and macOS. MP3 decoding and volume control require no external player. Linux uses the system audio backend (normally PulseAudio or ALSA). SoundFlow's notices ship in `Audio/SOUNDFLOW-NOTICES.txt`. The embedded default WAV is a generated two-note signal. Devices and decoder streams are opened lazily on a background task and released after playback; failures are logged and shown in the map panel.

Manual validation should cover default/custom MP3 playback, live volume changes, cancellation, missing/invalid files, safe-zone and friendly-player exclusion, burst coalescing, operation with the map closed, and Windows/Linux/macOS output devices. User settings `MapHostileSoundEnabled`, `MapHostileSoundVolume` and `MapHostileSoundFile` need no database migration.

Resource discovery audio uses `ResourceAlertSoundService` and the same `AlertSoundPlayback` coordinator as hostile audio. Each service owns its own player, default signal, volume and opt-in settings. The map and audio share `ActivityResourceFilter.ShowsTier`, including per-offset minimum enchantments. Resource audio also follows hidden families, Seen resources and Mobs switches; possible spawn spots never generate notifications. It works with the map window closed.

The tracker emits resource arrivals only from confirmed live context, on nonempty node/resource-mob appearance or an identity/enchantment change. Previously matching resources, charge-only updates, movement and depletion are silent; depletion removes the node, allowing a later respawn to notify again. Changing filters does not play sounds for resources already on the map. Bursts share one sound per three seconds, with no queued or overlapping resource sounds. Hostile settings remain independent.

The embedded `Audio/resource-alert.wav` is an original 480 ms, softly decaying three-partial chime, not a Path of Exile asset. Its peak amplitude is 0.20 versus 0.32 for the hostile signal; resource volume defaults to 35% and automatic audio starts disabled. `MapResourceSoundEnabled`, `MapResourceSoundVolume` and `MapResourceSoundFile` persist without a migration. Check matching/nonmatching nodes and mobs, per-tier enchantments, duplicate packets, depletion/respawn, live volume and independent hostile/resource toggles when validating audio.

## Crafting calculator

The Crafting sidebar page is a local desktop feature. `CraftingCatalog` lazily parses the existing embedded `processed_items.json.gz` and localized `items.json.gz` on a background task. It includes equipment enchantments, refining, consumables, components and alternative material recipes, with exact `amountcrafted` batch sizes and `maxreturnamount` caps (notably nonreturnable artifacts). Search accepts English/Russian names and market IDs; results are capped at 150 in a bounded virtualizing list. Recipe exchanges involving currencies, gold, standing or product returns are excluded because they require a different cost model. The bundled snapshot updates with the application's reference data; no submodule change or migration is needed.

`CraftingCalculator` rounds requested output up to complete crafts. For each input, required = crafts × recipe quantity; expected return = min(required × return rate, per-craft return cap × crafts); net material cost = (required − expected return) × unit price. Upfront silver includes all required materials, recipe silver, entered station fees and buy-order fees on the full purchase. Effective cost credits returns at the same input price without recrafting them. Net revenue subtracts sales tax and, for sell orders, the setup fee. Break-even is effective cost / (actual output × net sale fraction). Missing prices stay nullable; explicit manual zero means free materials. Return on cost is unavailable when cost is zero. Station fees and return percentages come from the game's displayed values; focus opportunity costs, journals, transport, nutrition and recursive intermediate crafting are excluded.

`CraftingPriceService` requests public AODP `/api/v2/stats/prices` snapshots from `west.albion-online-data.com`, `east.albion-online-data.com` or `europe.albion-online-data.com`, selected explicitly as Americas/Asia/Europe. Requests are scoped to one city, material quality 1 and the selected output quality; IDs are escaped, batches are capped at 50, and successful responses are cached for five minutes. Instant purchases use minimum sell prices, buy orders use maximum buy prices; sell orders use minimum sell prices and instant sales use maximum buy prices. Per-price timestamps flag observations older than 24 hours. API zero prices are unavailable. Manual overrides survive refresh and can be cleared with Use market prices. Navigation cancels pending price requests; version tickets discard obsolete responses. These hosts must be allowed by the deployment network policy; an API failure leaves manual calculation available.

Crafting search indexes both localized names, the market ID and the tier/enchantment label through `CraftingSearch.Normalize`. The same Unicode normalization, case folding, punctuation/whitespace handling and Cyrillic е/ё folding apply to queries. Russian names are retained on catalog entries for display and fall back to the base item for variants without their own localization.

## Runtime crash investigation

Desktop entry points install `RuntimeCrashLog` before Avalonia starts. The UI dispatcher and unhandled managed worker threads write a bounded `logs/runtime-crash.txt` (one previous file is retained), including UTC, PID, version, runtime/OS, exception stack and the last rendered map's ID/layer/count summary. The snapshot is an immutable string: fatal handlers never lock the tracker or marshal to a potentially blocked UI. The dispatcher handler records failures without marking unknown exceptions handled; normal Main-loop handling and terminating worker errors still terminate. Native access violations, GPU-driver termination, out-of-memory and external process kills cannot be reliably recovered or recorded this way; on Windows also inspect Event Viewer › Windows Logs › Application.

Map refresh failures are logged once per failing stretch, clear the stale scene and retry the next snapshot. Managed rendering failures skip the broken frame and retry when a new scene arrives; this does not swallow native access violations or out-of-memory errors. NaN/Infinity positions and headings are rejected before use, and the renderer falls back to a circle for an invalid heading. Validate with synthetic failing features and a subsequent valid frame, plus a disposable worker process that throws an unhandled exception. No database migration is required.

The update timer uses a guarded Task rather than `async void`: concurrent checks are skipped, exceptions are logged and the gate is released for the next check. Nonfinite, nonpositive or excessively large remote intervals use safe defaults. A check finishing during shutdown cannot install an update. Windows updates intentionally close the client and the Inno installer starts it again; the log explicitly identifies this intentional exit and the target version. An apparent restart alone does not establish a crash. No automatic recovery/restart loop is registered for ordinary application crashes.


### City market comparison

The Market prices page follows Crafting in the main navigation. `MarketCatalog` joins the bundled localized market IDs to game item metadata, including non-craftable raw resources and drops. Item families can be narrowed by tier, enchantment, quality and minimum IP. IP comes from the actual per-variant `@itempower`, plus quality (0/20/40/60/100). Missing IP is never inferred from tier.

`CraftingPriceService.GetMarketsAsync` shares one singleton transport/cache between Crafting and Market prices for all three regions. Prices and missing rows are cached per region/city/item/quality for five monotonic minutes, rather than per exact request URL. A serialized request gate rechecks the cache after waiting, coalesces overlapping callers (including simultaneous explicit refreshes), and groups identical missing item sets across cities/qualities; cached subsets do not require HTTP. Encoded URLs are packed up to 3,500 characters, leaving headroom below the upstream 4,096-character limit. A 60-ID fixture fits in one request instead of three 20-ID requests. HTTP starts are spaced at least one second apart across both pages. HTTP 429 respects Retry-After/RateLimit-Reset with no automatic retry, and fresh cache entries remain available during cooldown. The cache trims from over 20,000 cells to 16,000 oldest-first after a successful load. The crafting adapter retains normal-quality ingredient quotes. Refresh bypasses older entries; successful batches survive cancellation of a later batch. Leaving the page cancels outstanding requests, and generation checks prevent old responses from replacing a newer selection.

The Market toolbar has a searchable English/Russian/ID item picker, scroll-safe sliders, city chips, and an optional character-IP/fees expander. Equipment defaults to IP-range cards (25/50/100 IP); each card selects the best eligible offer across the selected cities, with explicit empty ranges, quality, snapshot age, net unit/total cost and price per IP. Bands use floor(IP / interval), so fractional character IP immediately below a boundary stays in the lower range. Buying minimizes cost; selling maximizes net proceeds. Cards sort by IP, total or unit price per IP; missing values remain last. The city table is still available, and items without IP automatically use it. Seven city markets start selected; Black Market is an optional eighth market and has buy orders only. The selected family's matching IDs/qualities are loaded for all eight markets together so changing cities, quantity, fees, action, age, minimum/character IP, grouping and sorting makes no price HTTP calls. Changing item, tier/enchantment, quality or region schedules a debounced cache-aware load. Character profile updates also recalculate locally. No History endpoint or speculative order-volume data is used.

The calculator chooses each city's best matching variant, minimizes purchase cost or maximizes net sale proceeds, and includes applicable sales tax / order setup fees. Instant buys use sell minima, instant sells use buy maxima, and order estimates use the corresponding competing quote. Quantity multiplies the snapshot price; AODP has no order-depth/available-quantity data, so totals do not prove that the requested volume can fill. No cross-item arbitrage profit is claimed. Zero/missing prices are unavailable. Quotes older than the chosen maximum age, unknown-time quotes (except explicit Any age), and timestamps more than five minutes into the future are excluded.

Character IP has an automatic captured-profile mode and a manual bonus fallback. The desktop subscribes to the shared `FullAchievementInfoEvent`, the same decoded levels uploaded to AFM by Specs; it does not scrape the site or add an undocumented authenticated API. A confirmed character/server context is required. Compact level-100 entries and explicit elite levels are resolved by achievement ID using the shared reference service. `CharacterMasteryService` reads the bundled Destiny Board `baserewards`/`eliterewards`, applies item-power patterns, tier gates and level limits, includes cross-specialization bonuses, then applies each item's mastery modifier to the total skill bonus. Base IP and quality do not receive this multiplier. Overcharge and awakened bonuses are excluded.

Up to 20 character/server snapshots are retained locally in `data/character-mastery.json`, with an atomic serialized write and a bounded persisted size. The page displays the source character, region and capture age. Rejoin the game with capture enabled to obtain/refresh a full snapshot; an existing AFM website profile is not downloaded on first use. Without captured levels, choose manual input or base IP. No database migration, new credentials, external dependency or shared-core pointer update is required.

Both Crafting and Market prices expose shared tier, rarity/enchantment and quality choices alongside the item picker/search. These combine with text search (and the crafting category). Market families require one variant satisfying all three filters; the same predicate restricts price candidates. Crafting quality filters retain recipes supporting that output quality and synchronize the output price quality. Any quality includes single-quality resources. Incompatible selections clear their dependent calculation, while a matching selection stays visible within the 150-result cap and retains manual prices across list refreshes.


AODP HTTP clients must negotiate compression: the upstream [non-gzip throttle](https://github.com/ao-data/albiondata-server-rails/blob/main/config/initializers/rack_attack.rb) allows only one uncompressed API request per five minutes. `CraftingPriceService.CreateHttpClient` enables automatic gzip/deflate/Brotli decompression and identifies the client. On HTTP 429, the shared service respects `Retry-After` / `RateLimit-Reset`, pauses new requests for that region (including Refresh), and shows the reset time. Valid cached quotes remain available. No automatic retry loop is used. Numeric strings in price/quality JSON fields are accepted; HTTP status, timeout and invalid-JSON errors have distinct UI messages.

Market search projects each family onto variants matching the current tier/enchantment/quality and text query. Single-variant results display that variant's localized name, full market ID and tier/enchantment, rather than a fixed T4 representative. Multiple variants have an explicit count, and selection is preserved by family key. Tier-specific text cannot match a hidden variant excluded by the numeric filters.

### Instance recognition: original Mists mechanism and Abbey/Depths adaptation

Research baseline: [upstream desktop bc84dc7](https://github.com/JPCodeCraft/AlbionDataAvalonia/tree/bc84dc7ecd48eb21273aecc9eaeb05a991298dee), its original [Mists integration 47cf641](https://github.com/JPCodeCraft/AlbionDataAvalonia/commit/47cf641250f27c776376417c4d4a9565cb06ad7d) and the pinned shared core's `Locations/MistsLayoutRecognizer.cs` / `tools/generate_activity_world.py`.

There are three independent steps. `AlbionLocations` classifies the raw Join location ID (`@MISTS@…`, `@MISTSDUNGEON@…`, `@HELLDUNGEON@…`); the UUID is an instance identity, not a layout. `ActivityInstanceMetadata.FromTransition` can map a reported game map ID to a master, when ChangeCluster supplies one. Neither step establishes rotation. An outdoor Mists entry through a wisp often supplies no layout, so fixed spawned objects determine both master and turn.

Upstream subscribes to `NewMistsWispSpawn` and `NewMistsBorderExit`. The shared envelope reads object ID at key 0 and a world position at key 1. Its generated reference contains 23 outdoor masters; generation takes already resolved wisp/border-exit positions from AlbionWorld features and rounds to half units. Abbey is explicitly excluded there because that source has no published Abbey features. The recognizer compares all masters at four clockwise quarter turns, `(x,z) -> (z,-x)`, with a 1.5-metre component tolerance. It needs at least two matches, a unique best score and a sufficient lead over the runner-up (unless all observations match). The tracker accepts current-connection observations from a ten-second pre-entry window; the resulting `Layout` and `LayoutTurns` enter Live and recorded visit metadata. The view rotates template geometry, never observed positions. A successful template lookup alone cannot replace this recognition step.

Abbey now subscribes to `NewMistsDungeonExit` with the existing shared envelope; no new Photon parser or core pin is added. Its 14 exact `MistsDungeonExit` template points identify the master and quarter-turn. All four rotated exit sets are disjoint at the matching tolerance in the bundled master. Two distinct matching exits are still required; duplicate packets cannot confirm a turn. The single-master offline fallback continues to select local data but does not invent an orientation. Until confirmed, Live/History display the path and observations on a grid. Recognized rooms, exits and possible chest spots turn together.

Both outdoor Mists and Abbey observations now carry object ID, instance ownership and pending Join attempt, as the Depths observations already do. A pre-response spawn burst on the same socket cannot rotate the map being left. Only a successful matching Join binds that burst to the new map; failed/superseded attempts, stale bursts and foreign receiver generations do not transfer. Placements are cached per server, character and exact raw map ID for process lifetime, so re-entry without another spawn burst retains the turn. This also prevents adjacent Mists instances on one connection from sharing the old ten-second pool. Duplicate positions are removed before the original outdoor recognizer is called.

The Depths already used the same matching principle, but part of the generated reference used *compound decoration origins*. Those are not world-object positions: the level-1 upward exit decoration at `(115,-15)` contains its actual exit at local `(0,3)`, turned 180 degrees, giving `(115,-18)`. A resurrection decoration at `(65,-215)`, turned 270 degrees, contains its shrine at `(3,0)`, giving `(65,-212)`; another slope decoration adds four metres. Downward exits add five metres. These offsets exceed the 1.5-metre tolerance; increasing that tolerance would hide inaccurate input.

`generate-depths-map-data.py` now expands fixed exit/shrine compounds using [`cluster/tiles.xml` at the same game-data revision as the templates](https://github.com/ao-data/ao-bin-dumps/tree/1a469e53de028c5f85cdd80505f10cbd0a2515cf), their selected layers, nested scale/rotation/translation, and exact object tile names. Broken/decorative exits do not become landmarks. It shares `template_geometry.py` with the resource-spawn exporter; regenerating resource candidates yields identical data. Direct altar node positions, random camp-slot semantics and recognition confidence are unchanged. The generated reference and visible possible exit/shrine POIs use the corrected coordinates. This proves and fixes a reference-data mismatch; it does not establish which event parameters the current Windows game sends.

Validation uses an external fixture, outside the repository test suite: decoded production subscriptions and Join lifecycle for outdoor Mists/Abbey/Depths, four rotations, duplicate/malformed/outlier rejection, offline map loading, re-entry caching and native Live/History geometry. Numeric compound examples above are checked independently of POI-to-recognizer round trips. Existing PoW tests remain the repository test suite. Live Windows packet capture remains outstanding: confirm key 0/key 1 envelopes for Abbey exits and the five Depths events. No arbitrary coordinate-key fallback or guessed orientation is introduced; packet diagnostics must be enabled before entry if recognition still receives no landmarks.
